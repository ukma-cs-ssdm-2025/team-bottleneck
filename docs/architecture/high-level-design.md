# High-Level Design: Parking Management System

## 1. Архітектурний стиль
- Обрано **3-шарову client-server архітектуру**:
  - Presentation layer: React UI (Web/Mobile).
  - Application layer: Python (бізнес-логіка, REST API).
  - Data layer: PostgreSQL.

## 2. Основні компоненти
- **React UI** — інтерфейс для користувачів.
- **REST API** — точка входу для запитів.
- **Python App (Django/Flask)** — бізнес-логіка:
  - Authentication Service.
  - Parking Management Service.
  - Payment Service.
  - Notification Service.
- **DAO + PostgreSQL** — збереження даних.
- **External Systems**:
  - Payment Gateway.
  - Email/SMS Provider.
  - Maps API.

## 3. Діаграми UML
- Component Diagram — взаємозв'язки компонентів.
- Deployment Diagram — інфраструктурне розгортання.

## 4. Обґрунтування вибору
### PostgreSQL:
- Найкраща підтримка з Django ORM.
- ACID, надійність, складні запити.
- Підтримка JSON полів.
- Широка підтримка у спільноті.

### Чому не MongoDB?
- Наші дані реляційні (бронювання, транзакції).
- Mongo складніше інтегрувати з Django.

### Чому не мікросервіси?
- Невелика команда, простіше підтримувати моноліт з чітким поділом шарів.
- Мікросервіси мають сенс лише при великому масштабі.

## 5. Відповідність вимогам
- FR: пошук місць, бронювання, оплата — реалізовані окремими сервісами.
- NFR: продуктивність (PostgreSQL + кеш), надійність (backup, ACID), безпека (HTTPS, TLS 1.3, AES-256).

## 6. Висновок
Обрана архітектура:
- Проста для команди.
- Враховує вимоги користувачів і NFR.
- Легко масштабується і підтримує інтеграцію із зовнішніми системами.

## 7. Гнучкість та можливості еволюції
- Наша архітектура заснована на чіткій ізоляції клієнта від бекенду (через REST API).
- Це дозволяє в майбутньому замінити або доповнити веб-клієнт мобільним застосунком (React Native, Flutter, iOS/Android) без змін у бізнес-логіці та базі даних.
- Таким чином, еволюція продукту від веб-сайту до мобільного додатку не потребує перебудови архітектури.
